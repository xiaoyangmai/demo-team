# Illustrated learning comic

Make the requested principle understandable through what characters do and what changes. Keep the task's topic, audience and output contract; a successful file export is not proof of learning.

1. Plan four beats before any image call: an appealing everyday goal, a believable difficulty, a meaningful choice, and its visible consequence. For each beat, name one pointable fact—where the key object is, or which cue is showing—that would be false if the child used the plausible wrong choice. Show that fact and remove props that do not carry it. Fix hair, clothing and that small prop set. Log every panel's end state: who holds the driving object, where it rests, and what the cue shows. The next panel starts from that end state; do not draw a finished outcome and later an earlier handoff. When the principle is a changed sorting or comparison rule, cross the attributes so the old rule and the new rule place the same object differently, and keep the current wordless cue large on the container. Otherwise use this topic's own decisive relation; do not import a sorting task. For scientific comparisons, change one condition and hold the others steady.

2. Draft all four prompts, then generate. Exactly two large ordered panels per page, one frozen moment each; the change is the difference between panels, not a sequence inside one still. Do not let a four-panel grid override the brief. Finish both panels' end locations in the prompt, and keep it short enough that the right panel is not cut off. No words, letters, speech balloons or watermarks; a pictorial cue the lesson needs stays large and stable. Repeat a compact character and prop bible. This backend treats a source image as an edit: use one only to keep character appearance, not a previous full page whose pose or object locations must change. Do not add a reference-generation pass. Call `image_generate` once each for pages 1–4 before any repair. One entry per `tool_call`; a multi-entry batch is rejected. Never substitute diagrams, SVG, emoji or placeholder art.

3. Inspect the actual images with `vision_analyze`: who acted, where the key object ended, and whether the pointable fact and state order are visible. Do not claim a check from the prompt. Only after four pages exist, use at most one more call, within budget, to redo the page whose missing fact most breaks the principle. If that redo fails, keep the clearer version of that same page and stop image calls. Do not spend the spare call before page 4 exists, and do not stop the comic early. Copy the returned files into the delivery directory and keep extensions that match their bytes.

4. Write captions and alts from the vision report, not the plan. Name only a relation the image shows; do not invent an unseen agreement, a finished timer, a handoff direction, or a placement that is missing. If the still is ambiguous, narrow the caption rather than narrating the plan. Then write two application questions with different changed conditions. Every option is one short action, not a strategy slogan; put the explanation in its feedback. First name the misunderstanding each wrong choice represents. A well-intentioned child could choose it: a useful step at the wrong time, an old rule after the condition changed, or incomplete evidence. Do not use insult, blame, or doing-nothing as an easy contrast to the sole kind answer. Length, politeness and detail must not reveal the correct answer. Feedback explains the decisive condition without a fact absent from the page or question.

5. Give the ending one concise takeaway and one safe, concrete action a child can try today. Avoid a generic moral that could be attached to any story. Use spoken Chinese and follow the caller's reading limits; do not solve ambiguity by making the correct choice a paragraph.

6. Write `lesson.json` and run the bundled `scripts/render.py <delivery-directory>` from this Skill's directory. It packages the four pictures, captions, quiz, retry/reset and completion state; do not rewrite its UI. Check the generated files and the manifest, then write the caller's result receipt with only checks actually performed. Do not edit project/profile files or inspect evaluation material.
